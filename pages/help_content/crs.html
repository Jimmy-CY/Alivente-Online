What is the CRS Reporting module?

The CRS module produces Common Reporting Standard (CRS) XML files for the OECD's Automatic Exchange of Information (AEOI) regime. It takes your account data from an Excel workbook, validates and cleans it, builds jurisdiction-specific XML that conforms to the OECD CRS schema, and tracks each annual filing from draft right through to acknowledgement by the receiving authority.

CRS is the OECD framework under which financial institutions report the accounts of foreign tax residents, so that information can be exchanged automatically between tax authorities. A Financial Institution does not file directly with each receiving country — it files with its own home tax authority (in your case the Cyprus Tax Department's AEOI portal), which then routes the data internationally. This module produces the XML the FI uploads to that portal.

What it does
Master data
Configure the receiving jurisdictions you report into, and the Financial Institution(s) that lodge the filings.
Excel ingest
Download a bundled template, fill one row per reportable account, and upload it. The system parses, normalises and validates every row.
XML generation
Build OECD-conformant CRS XML — one file per receiving country, or a single combined file where a jurisdiction is configured for it.
Schema validation
Every generated file is validated against the bundled OECD XSDs before it is made available for download.
Lifecycle tracking
Each submission moves through draft → closed → submitted → acknowledged / rejected, with the status recorded for audit.
Download & view
Download files individually or as a ZIP, and view any generated XML inline before you submit it.
Current schema: The module targets OECD CRS XML schema version 2.0, accepted by all CRS jurisdictions for calendar-year 2025 data filed by 31 May 2026. A schema upgrade (informally "CRS 2.0", schema v4.0) becomes mandatory for 2026 data filed in 2027 — that is a planned future change.
The end-to-end flow

Two one-time setup steps, then an annual filing cycle you repeat each reporting period.

One-time setup
1. Country Configurations — one row per receiving jurisdiction you report into, each with its schema version, output strategy, reference-ID templates and TIN validation. A baseline of 30 countries (Cyprus plus 29 seeded) ships ready to use.
2. Reporting Financial Institution(s) — the entity that lodges the return, with its address, contact details, and one or more Identification Numbers.
Annual filing cycle
1 Start submission — pick the FI and the period end. A draft is created and a unique MessageRefId is generated.
2 Download the Excel template and fill one row per reportable account.
3 Upload the workbook — it is parsed, normalised and validated synchronously, with a diagnostic summary.
4 Generate XML — one file per receiving country (or a single combined file where configured), each validated against the OECD schema.
5 Review & close — once every file is valid, close the submission to freeze it.
6 Submit externally — upload the XML to the tax authority's portal, then mark it submitted here.
7 Record the outcome — mark the filing acknowledged or rejected when the authority responds.
The full detail of each step — the Excel layout, what the parser does, every validation rule, and how the XML is built — lives in the Submissions help.
Who can do what

CRS access is governed by two permissions, granted per user in User Administration → Permissions.

can_access_crs — read

Lets a user open the CRS pages and view, download and inspect everything — country configs, FIs, submissions and generated XML — but not change anything.

can_edit_crs — write

Required for any state-changing action: starting a submission, uploading Excel, generating XML, closing, marking lifecycle states, deleting, and adding or editing countries and FIs.

How it's enforced
  • URL gate — any request to a CRS page by a user without can_access_crs is rejected before the page even runs.
  • Per-action checks — every CRS action independently re-checks the right permission, so the URL gate is a safety net rather than the only line of defence.
  • UI consistency — write buttons are simply hidden from read-only users, so they aren't shown actions they can't perform.
Superusers bypass these checks and can perform any CRS action regardless of the two grants — the same as everywhere else in Alivente.
What the module deliberately does not do

Knowing the boundaries avoids surprises. These are intentional design decisions, not gaps.

No automatic transmission
The module produces the XML; you upload it to the tax authority's portal manually. The submission status is then tracked here by hand.
No FATCA
This is CRS-only. US reporting uses a separate IRS FATCA schema and is out of scope. US-resident accounts are automatically excluded from CRS files.
No CARF / DAC8 crypto reporting
Crypto-asset reporting uses distinct schemas and would be a separate module.
No UK HMRC reporting (yet)
For 2026, the UK still uses HMRC's bespoke combined CRS/FATCA schema, which this module doesn't implement. The UK becomes supportable once the schema is upgraded for the 2026 reporting year (filed in 2027).
The module's job stops at a validated XML file you can trust. Getting it into the portal — and any FATCA, crypto or UK obligations — remain separate, manual responsibilities.
Best practices
  • Set up master data once, reuse it every year. Countries and FIs are configured once and referenced by every submission — get them right and the annual cycle is mostly Excel work.
  • Let the parser do the cleaning. Many formatting issues (negatives, thousand separators, accents, date formats) are auto-corrected on upload — don't waste time pre-formatting the spreadsheet by hand.
  • Never submit a file that isn't valid. A submission can only be closed when every generated XML passes XSD validation, which is exactly what the portal expects. Trust the green check.
  • Keep the MessageRefId unique. The system generates it for you from the country's template; never reuse one across filings — the portal will reject a duplicate identifier.
  • If something's wrong after close, delete and redo. There is no in-place edit of a closed submission — deleting and re-creating keeps the audit trail unambiguous and issues a fresh MessageRefId.
What is a Country Configuration?

A Country Configuration is one row per receiving jurisdiction — the destination a CRS report is ultimately routed to. Each row controls whether the country is available when starting a submission, which schema version applies, how accounts are grouped into output files, the templates used to build the OECD reference identifiers and the output filename, and how TINs are validated for that jurisdiction.

Already seeded for you. A baseline of 30 jurisdictions ships ready to use — Cyprus plus 29 others. You only need to add or edit rows if you report into a jurisdiction outside that baseline, or want to change a strategy, template or flag.
Where to find it

From the CRS landing page, open Country Configurations. The table lists every configured jurisdiction; the eye icon opens a read-only detail view of all its settings, and add / edit / delete actions require write access.

Each field explained

The detail view groups the fields into three sections — Basic, Reference ID Templates, and Validation.

Basic
Code
The ISO-3166 alpha-2 code (e.g. CY, DE, FR). This is the primary lookup key, so it must be a valid two-letter code recognised by the OECD.
Name
The display name shown throughout the UI. Cosmetic — the code is what drives behaviour.
Status (Active)
When inactive, the country is excluded from new submissions. Use this to retire a jurisdiction without deleting its configuration.
Schema Version
The OECD schema version in force for this jurisdiction — currently 2.0 for all rows. This will be bumped jurisdiction-by-jurisdiction when the schema upgrade lands.
Receiving Country Strategy
Either Split by Residence (the default — and what Cyprus uses) or Combined Domestic. This decides how accounts are grouped into output files — see the Strategies tab.
Notes
Free-text operational notes for your own reference — not used by the system.
Last Updated
Timestamp of the most recent change to this configuration — informational.
Reference ID Templates

These templates control the OECD identifiers and the output filename the builder generates for this jurisdiction, so each one matches the receiving authority's conventions. They use placeholder tokens that expand at generation time.

Placeholders: [SENDING_FI_IN] — the sending FI's Identification Number  ·  [YEAR] — the reporting year  ·  [UUID] — a generated unique component for global uniqueness  ·  [YYYYMMDDHHMM] — a timestamp to the minute  ·  [CURRENT_DATE] — the file generation date.
Message Ref ID
Template for the file-level MessageRefId — the unique identifier for the whole submission. Must be unique across all filings, or the portal rejects it. Example: [SENDING_FI_IN].[YEAR]_[UUID].
FI Doc Ref ID
Template for the DocRefId of the reporting-FI element. Example: [SENDING_FI_IN].[YEAR]_[YYYYMMDDHHMM]_[UUID].
Account Doc Ref ID
Template for the DocRefId of each account / controlling-person record. Each record gets its own unique value. Example: [SENDING_FI_IN].[YEAR]_[YYYYMMDDHHMM]_[UUID].
Output Filename
Template for the generated XML filename. Example: [SENDING_FI_IN]_[CURRENT_DATE].xml.
Validation
TIN Regex
A regular expression used to validate Tax Identification Numbers for accounts reported into this jurisdiction. The default [a-zA-Z0-9]* accepts any alphanumeric TIN. Tighten it for a jurisdiction with a stricter TIN format.
How accounts become files

The receiving-country strategy is the most consequential setting on the row. It answers one question: how should reportable accounts be grouped into the XML files you submit?

Split by Residence (default — used by Cyprus)

One XML file per receiving country, each containing only the accounts of tax residents of that country. This is standard OECD behaviour and the right strategy for most jurisdictions, including Cyprus.

Example: an FI with accounts across France (5), Spain (4) and Italy (3) produces three files — one FR, one ES, one IT — each holding only that country's residents.

Combined Domestic

A single file for the FI's home jurisdiction, containing foreign-resident accounts together with domestic-resident accounts. This suits an authority that prefers one ingestion file with domestic accounts included.

In combined mode the builder also groups multiple controlling persons under a single account element rather than over-decomposing, keeping the record count compact without changing its meaning.

Two automatic exclusions

Regardless of strategy, the builder applies two rules so you never accidentally over-report:

US residents are always dropped. They are out of scope for CRS (reportable under FATCA instead). The parser flags them and the builder excludes them with an informational message.
Domestic residents are dropped in split mode. For split-by-residence jurisdictions, accounts of the FI's own residence-country residents are excluded (they fall under domestic tax rules). Combined-domestic jurisdictions are exempt — they intentionally include domestic accounts.
Best practices
  • Leave the seeded baseline alone unless you have a reason. The 30 shipped jurisdictions cover the common cases. Add a row only when you report into something outside it.
  • Use the right strategy. Most jurisdictions — including Cyprus — use Split by Residence. Switch a row to Combined Domestic only when that authority asks for a single combined file that includes domestic accounts.
  • Match the reference-ID templates to the portal. The MessageRefId, DocRefId and filename templates exist so each jurisdiction's output matches what its portal expects — only change them if the portal's conventions differ.
  • Deactivate, don't delete. To stop using a jurisdiction, set it inactive. That removes it from new submissions while preserving the configuration.
  • Get the ISO code exactly right. It's the primary key and drives validation. A wrong or non-OECD code will cause downstream XSD failures.
  • Trust the exclusions. If a count looks lower than your raw data, the US and domestic exclusions are usually why — that's correct behaviour, not a missing record.
What is a Reporting FI?

A Reporting Financial Institution is the entity that lodges the CRS return. Its details flow into the OECD MessageHeader of every XML file it produces — legal name, residence country, address and contact information. You can configure more than one FI if you report on behalf of several entities (group-level reporting).

Each submission references exactly one Reporting FI. The FI is master data — set it up once and select it whenever you start a new submission.
Where to find it

From the CRS landing page, open Reporting Financial Institutions. Click Add Reporting FI to create one, or Edit to update it. Adding and editing require write access.

The institution record
Legal name
The institution's legal name exactly as it should appear in the OECD MessageHeader.
Residence country code
The ISO-3166 alpha-2 residence country of the FI (e.g. CY). This also determines which accounts count as "domestic" for the exclusion rules.
Structured address
The multi-field address that populates the OECD CRS address element.
Contact name, email & phone
Contact details echoed into the MessageHeader.
Active
When unticked, the FI is hidden from the start-submission workflow without being deleted.
One FI, several Identification Numbers

The OECD schema allows a Financial Institution to carry multiple Identification Numbers — for example, a different IN per receiving jurisdiction. On the FI edit form you add one or more IN rows, each describing a single identifier. The IN also feeds the [SENDING_FI_IN] placeholder used in the country reference-ID templates.

IN value
The identification number itself.
Issued by
The ISO country code of the authority that issued the number.
IN type
The OECD IN-type code — e.g. TIN (Tax Identification Number) or GIIN (Global Intermediary Identification Number).
Add an IN for each jurisdiction the FI needs to identify itself to. Each is scoped by its issuing country and type, so the same FI can present the right identifier in each file.
Best practices
  • Match the legal name precisely. It goes straight into the MessageHeader the authority reads — use the exact registered name, not an informal one.
  • Add every IN you need up front. If you report into several jurisdictions, set up the matching INs once so each generated file carries the correct identifier.
  • Keep contact details current. They are echoed into every filing's header and are what an authority uses to reach you about a return.
  • Deactivate rather than delete an FI you've stopped using — it keeps the historical submissions intact and reversible.
What is a Submission?

A Submission is one annual filing — it anchors the whole reporting cycle for a Financial Institution and a reporting period. It carries the period, the FI, the uploaded Excel, the generated XML files, the validation outcome, and the external-submission status. This is where the day-to-day work happens.

A unique MessageRefId is generated when you start the submission and stays with it for life.
The uploaded Excel workbook is the data source for that filing.
One or more XML files are generated from it, each with its own validation result and record count.

The tabs in this help cover, in order: the lifecycle, the Excel template, what happens on upload & parsing, every validation rule, how to fix problems, how the XML is generated, and the nil-return path.

The five states

A submission moves forward through a fixed set of states. Transitions are linear with no rollback — there is deliberately no "re-open", so the audit trail stays unambiguous.

draft → closed → submitted externally → acknowledged / rejected
DRAFT

Submission created, header set, Excel may be uploaded, XML not yet finalised. Allowed: edit header, upload / remove / replace Excel, generate or regenerate XML, close (once valid), delete.

CLOSED

Internally finalised — validation passed and XML files frozen, awaiting upload to the portal. Allowed: mark submitted externally, delete. Excel upload and regeneration are no longer available.

SUBMITTED EXTERNALLY

Files uploaded to the authority's portal, awaiting their response. Allowed: mark acknowledged, mark rejected, delete.

ACKNOWLEDGED

Terminal positive state — the portal confirmed acceptance. Allowed: delete (audit cleanup).

REJECTED

Terminal negative state — the portal returned a rejection. Allowed: delete.

Delete works in every state. Discovering a problem late (e.g. a misclassified account in a closed submission) is common — rather than amend, you delete and re-create. Deleting removes the Excel and every generated XML file from storage before removing the submission, then a fresh submission gets a new MessageRefId.
The data template

From the submission detail page, click Download Excel Template. You'll get the bundled workbook with the exact column layout, header naming and dropdown validation the parser expects. Fill in one row per reportable account, then upload it back.

Use the template as-is. Column positions and header names matter — the parser validates them. Don't rearrange columns, rename headers, or delete the header row.
Respect the dropdowns. Where the template offers a dropdown (e.g. holder-type and code fields), pick from it. Free-typing values that aren't recognised will surface as validation errors on upload.
Account holder types matter. The holder type drives how each account is built in XML — an individual, a passive entity reported with its controlling persons inline, or an entity whose controlling persons are reported separately. The Validation Rules tab explains the rules the parser enforces here.
You don't need to pre-format values. The upload step cleans a lot for you — currency amounts, date formats, accents, spacing and codes. Concentrate on getting the facts right; the system handles presentation. See Validation Rules for exactly what's auto-corrected versus what blocks.
What happens when you upload

Upload runs synchronously — you get the result immediately. Behind the scenes the workbook passes through a pipeline. Here's what each stage does, in plain language.

1 Read & type-check
Every row is read and validated for required fields, code formats, and inter-field consistency (for example, controlling persons are only allowed on holder types that can carry them).
2 Normalise
A consistent set of cleanups is applied: trimming whitespace, uppercasing ISO codes, emptying blanks, and reformatting amounts, dates and text. This is the auto-correction layer detailed in the next tab.
3 Cross-check reference data
Cleaned values are checked against the OECD-recognised lists — ISO country codes, ISO currency codes, holder-type and IN-type enumerations — and TINs against the jurisdiction's TIN regex, so anything that would later fail the schema is caught now.
On success the file is attached to the submission and a parse summary is shown.
On error the upload is rejected with a diagnostic and the submission stays in draft, awaiting a corrected workbook. Nothing partial is saved.
What's auto-fixed vs what blocks

There are two kinds of rule. Auto-corrections quietly clean your data so it conforms. Blocking errors stop the upload because the system can't safely guess your intent.

Auto-corrections (applied for you)
Monetary amounts — negatives are clamped to zero, thousand separators are stripped, and values are reduced to whole integers.
Dates — reformatted to YYYY-MM-DD. For ambiguous input the day-first (DD/MM/YYYY) reading is assumed.
Names & addresses — restricted to letters, digits and a safe punctuation set ' . , / - ( ) #. Accented characters are transliterated (e.g. ø→o, ß→ss); anything with no mapping is dropped, and runs of whitespace are collapsed.
Codes — ISO country and currency codes are uppercased and trimmed; empty cells are emptied to null rather than left as blank strings.
Blocking errors (you must fix these)
Invalid currency code — must be a recognised ISO 4217 code.
Invalid country code — must be a recognised ISO 3166-1 alpha-2 code.
Unparseable date — if a date can't be read at all, it can't be reformatted, so it stops.
Missing required field — a row that omits a mandatory value can't be reported.
Holder-type / controlling-person mismatch — the holder type and the presence (or absence) of controlling persons must be consistent. A passive entity reported as an individual-style holder, or controlling persons attached to a holder type that can't carry them, is rejected.
Reportability rules (applied at build time)

Beyond cleaning and validating, two rules decide whether a row is reported at all:

  • US residents are excluded (FATCA, not CRS), with an informational message.
  • Domestic residents are excluded for split-by-residence jurisdictions; combined-domestic mode intentionally keeps them.
Entity decomposition (CRS101 / CRS102 / CRS103)

Account-holder types are handled per the OECD rules when the XML is built:

CRS102 — a passive entity whose controlling persons are carried inline within the same element.
CRS103 — an entity reported on its own. Its controlling persons are split out into separate CRS101 elements, because the OECD validation rules say controlling persons don't belong on a CRS103 element.
CRS101 — a controlling person (natural person) reported against an underlying entity holder.
Combined-domestic mode — multiple controlling persons are grouped under a single CRS101 element keyed on the account, avoiding record inflation without losing any information.
When the upload reports a problem

The diagnostic tells you which rows and fields need attention. The fix depends on the kind of message.

Informational messages — no action needed

Notices such as "US-resident account excluded" or "domestic account excluded" are telling you the system did the right thing. They explain why a count is lower than your raw row count — they're not errors.

Blocking errors — fix in Excel and re-upload

Invalid codes, unparseable dates, missing required fields and holder-type mismatches all need correcting in the spreadsheet. Edit the flagged rows, save the workbook, and upload it again.

The submission stays in draft until a clean workbook is accepted, so you can iterate as many times as you need.

Why some things can only be fixed in Excel: the system can clean formatting it can interpret (a stray comma, an accent, a date in the wrong order). It will not guess at meaning — if it can't tell which country XZ is, or what a blank required field should contain, only you can supply the right value.
From accounts to validated XML

Once a workbook is accepted, click Generate XML. The builder turns your parsed accounts into OECD CRS XML and immediately validates each file.

Output file set
Each receiving country's strategy decides the files: split-by-residence produces one file per country (residents of that country only); combined-domestic produces a single file with foreign and domestic accounts together. The filename follows that country's Output Filename template.
Exclusions & decomposition
US and (where applicable) domestic accounts are dropped, and entity holder types are decomposed into the correct CRS101 / CRS102 / CRS103 structure — as described in the Validation Rules tab.
Header & identifiers
The MessageHeader (MessageRefId, type, reporting period, timestamp) and per-record DocRefId values are built from the country's reference-ID templates, so each file and each record is uniquely identified as the OECD User Guide requires.
XSD validation
Every generated file is validated against the bundled OECD schema. The per-file result (valid or not, plus any schema errors) is shown on the submission detail page.
Review, then close

Inspect files with the inline XML viewer (the eye icon), or download them individually or as a ZIP. When you're satisfied, click Close Submission.

Close is gated. It's only available when the submission is in draft, at least one XML file has been generated, and every file is valid. If a file fails, fix the Excel, re-upload and regenerate — you can't close on a failing file.
When there's nothing to report

Some jurisdictions require a nil return — a filing that confirms there were no reportable accounts for the period. The module produces a valid nil-return XML for this case, so you can satisfy the obligation without any account data.

A nil return is a complete, schema-valid file in its own right — it carries the FI and period header with no account records. It moves through the same lifecycle (close, submit, acknowledge) as a normal filing.
Check first whether you need one. Not every jurisdiction requires a nil return, and some require it only in certain circumstances. Confirm the obligation with the receiving authority before filing one.
Best practices
  • Always start from a freshly downloaded template. It guarantees the column positions, headers and dropdowns the parser expects — an old or hand-built workbook is the most common source of upload errors.
  • Read the parse summary, not just the row count. Informational exclusion messages explain why the reported count differs from your spreadsheet — that difference is usually correct.
  • Fix once, regenerate, re-validate. After correcting Excel, re-upload and regenerate; the per-file validation tells you immediately whether you're clear to close.
  • Don't fight the auto-corrections. Negatives, separators, accents and date formats are cleaned for you. Focus your effort on the facts and the holder-type rules, which only you can get right.
  • Close only when every file is green — that's the same bar the portal applies, so a clean close means a clean upload.
  • To correct a closed filing, delete and redo. There's no re-open by design; a fresh submission gets a new MessageRefId and keeps the audit trail clean.
