Revenue Types — User Guide
Define when in the year revenue is collected (the seasonality pattern)

What are Revenue Types?

A Revenue Type defines the seasonality pattern of an income stream — in other words, which months of the year that income is actually collected.

Each Revenue Type is essentially a 12-month template made up of Yes/No flags. When you later create a Revenue record on a property and assign it a Revenue Type, the system uses this template to know when to count that income across the calendar year.

Two examples already in your system:
  • Monthly — all 12 months marked Yes. Use this for standard year-round rentals or any income collected every month.
  • Summer — May to October marked Yes, the rest No. Use this for seasonal lets, holiday rentals, or anything only earning in the summer months.
Where this fits in the bigger picture

Revenue Types are one of three Configuration pieces on the Revenue side that work together:

  1. Revenue Types (this page) — when income is collected (the months pattern)
  2. Revenue Line Types — what the income is called on the P&L (e.g. "Rental", "Levies")
  3. Revenues — the actual records: a property + a Line Type + a Type + an amount

Together these feed into the Profit & Loss Statement, where each month's revenue is calculated by applying the Type's pattern to the Revenue amounts on each property.

Permissions: This page is restricted to Superusers. Standard users won't see Configuration in the Financials menu.
Reading the Table

Each row is a Revenue Type you've defined. The 12 month columns show, at a glance, which months that Type collects income.

Column-by-column
  • Revenue Type — the name you gave it (e.g. Monthly, Summer).
  • Jan – Dec — one column per month, showing either Yes or No.
  • Details — an Edit button to modify that Revenue Type.
The colour coding

The cells are colour-coded to make seasonality patterns easy to spot at a glance:

  • Green — Yes   income is collected this month
  • Red — No   income is not collected this month
At a glance: A row that's all green is a year-round income pattern. A row with a clear green block flanked by red shows a seasonal pattern — like the Summer row, where you can immediately see income runs from May through October.
Adding a Revenue Type

Click Add New in the top-right to open the Add Revenue Type form. You'll see two things to fill in:

  1. Revenue Type Name — a short, descriptive name (e.g. Monthly, Summer, Winter, Quarterly).
  2. The 12-month checkbox grid — one checkbox per month.
How the checkboxes map to Yes / No:
  • Checked  =  income IS collected that month  →  saved as Yes
  • Unchecked  =  income is NOT collected that month  →  saved as No

The Add form doesn't show "Yes/No" labels — just the checkboxes. The conversion happens automatically when you save.

When you're done, click Save in the top-right. The Type appears in the list and is immediately available to assign to Revenue records.

Editing an existing Revenue Type

Click the Edit button on the relevant row. The form is identical to the Add form — the Name field is pre-filled, and the checkboxes reflect the current Yes/No pattern. Make your changes and click Save.

Editing has a downstream effect. If a Revenue Type is already in use by Revenue records on properties, changing its month pattern will retroactively change how those records appear in the Profit & Loss Statement. For example, switching Summer from May–Oct to Apr–Sep will shift every revenue record using Summer by one month in the P&L. If you need a different pattern, consider creating a new Revenue Type rather than editing an existing one.
Practical Tips
  • Name them by pattern, not by property. A Revenue Type is reused across many properties — Monthly, Summer, Quarterly all describe patterns. Avoid names like "Apolloneon Rental"; that belongs on the Revenue record itself, not the Type.
  • Start simple. Most portfolios only need two or three Types: Monthly covers nearly everything; add Summer (or Winter) for seasonal lets. Don't create a Type until you have a property that actually needs it.
  • Keep Monthly as your default. It's the most common pattern, and having it always available means you rarely have to think about Type selection when adding routine revenue.
  • Plan around your local seasons. "Summer" means different months in different countries — for Cyprus and Greece holiday lets, May to October is typical. Set the pattern based on when income actually arrives, not on calendar quarters.
  • Don't edit Types in active use — clone them instead. Editing changes the P&L for every Revenue record using that Type, retroactively. Safer pattern: create a new Type with the new shape (e.g. Summer 2026), then move the affected Revenue records to it one at a time.
  • Use the colour bands to sanity-check. After saving, glance at the row in the table. If Summer shows green in December, something's wrong — the visual makes mistakes easy to spot.
  • The Type doesn't store amounts — only the months. The actual € figure lives on the Revenue record. Two properties can both use Monthly with completely different rents.
