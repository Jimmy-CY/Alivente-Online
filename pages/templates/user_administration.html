What is User Administration?

User Administration is the central place to manage everyone who can log into Alivente Online. From this single screen you can:

  • Add new users
  • Edit existing user details (name, email, role, password)
  • Manage permissions — grant or revoke access to individual modules
  • Disable users so they can no longer log in (without losing their data)
  • Re-enable previously disabled users
  • Delete users permanently (only available once disabled)
How to get here

Administration System tab User Administration card.

Superuser only: User Administration sits inside the Administration page, which is itself Superuser-only. Regular users cannot reach this screen.
The user table

Every registered user appears as one row, with six columns:

User

A circular avatar (uploaded photo if available, otherwise the user's initials, or as a final fallback the first letter of the username), the user's full name, and their email address. "No email" is shown if none was set.

Role

A coloured badge: Superuser or User. See the Roles tab for what each one means.

Status

Active — can log in. Disabled — account exists but login is blocked.

Last Login

Date and time of the user's most recent login. Shows Never in grey if they've never signed in.

Date Joined

When the user account was originally created.

Actions

A row of small coloured buttons. The button set changes depending on whether the user is Active or Disabled — see the Actions tab.

The two roles

Every user has one role, shown as a coloured badge in the User table.

Superuser

Full administrative access. Superusers automatically have access to every module — the Permissions screen for a Superuser is informational only and any module checkboxes are ignored. Use sparingly — this role can do everything, including managing other users.

User

Standard access — the default role for new accounts. Module access is fully controlled by the Permissions screen.

Choosing a role: Default everyone to User and grant only the modules they need via Permissions. Reserve Superuser for the small number of people who genuinely need to administer the whole system.
Available actions

One header action and a set of per-user row actions.

Add User (top-right)

Opens the Add New User form, which collects:

  • Personal Information — First Name, Last Name, Username (required), Email Address
  • Password — Password and Confirm Password (must match)
  • Role & Status — pick User or Superuser, and tick Active so they can log in immediately
Per-user row actions
Edit (yellow)

Update the user's name, email, role or password. Always available regardless of status.

Permissions (teal)

Opens the Permissions screen, where you tick which of the 12 modules the user can access (Properties, Tenants, Suppliers, Expenses, Petty Cash, Financials, Invoices, Projects, Issues, Dashboard, Administration, Personal).

Superusers automatically get all 12 — the checkboxes are read-only for Superuser accounts.

Disable (red, only for Active users)

Blocks the user from logging in. Their account and data remain intact — nothing is lost. A confirmation popup asks you to confirm before applying.

Enable (green, only for Disabled users)

Restores login access for a previously disabled user. Replaces the Disable button on disabled rows.

Delete (red, only for Disabled users)

Permanently removes the user and all their associated data — meal plans, favourites and any other records. Cannot be undone.

Only available for users who are already disabled. The two-step requirement (Disable first, then Delete) is intentional — it forces a deliberate pause before destructive action.

Action button visibility: Active users show Edit, Permissions, Disable. Disabled users show Edit, Permissions, Enable, Delete.
Best Practices
  • Disable rather than delete — if someone leaves the team, disable their account. You can always re-enable later if they come back. Delete only when you're certain you'll never need their historical activity.
  • Default new users to "User" — grant least privilege. Add only the modules they need via Permissions. Promote to Superuser only when justified.
  • Be sparing with Superuser — this role bypasses the Permissions screen entirely. The fewer Superusers, the safer your system.
  • Watch for "Never" Last Login — an account that has never logged in is either a failed setup, a forgotten invitation, or a placeholder. Confirm it's intentional or chase the person to log in.
  • Email is important — it's where notifications go. Always set a real email when creating a user. "No email" accounts won't receive any system alerts.
  • Don't bother editing Superuser permissions — they're ignored. The Permissions screen for Superusers is read-only.
  • Use the avatar as a quick visual cue — users with profile photos appear immediately recognisable. Encourage your team to upload one in My Profile.
  • Test permission changes by logging in as that user — the cleanest way to confirm someone has the access you intended is to actually try it.
Don't disable yourself! If you disable your own account you'll be locked out at next login. There's no built-in protection against this — double-check the username before clicking Disable on yourself.
