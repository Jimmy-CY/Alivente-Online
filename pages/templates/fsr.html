What is the Issues page?

Issues is the central log of everything that needs attention across the portfolio — maintenance requests, tenant complaints, repairs, meetings, and anything else worth tracking. Every issue has a running Comments thread for updates, a Status that moves through a lifecycle, and a Date Logged for reporting.

What you can do here
  • Browse every open and historical issue across every property
  • Filter and search by text, country, property or status
  • Sort by Property, Date Logged or Status (click the column headers)
  • Add a new issue
  • Open Comments on any issue to read the discussion thread, post updates, and change status
  • Delete an issue permanently (Superuser only)
  • Generate three reports: Comments Report, Resolved Issues Report, Friday Status Report
Status lifecycle

Three statuses with a clear lifecycle:

  • Unresolved — the default state when an issue is first logged. Stays here while the team is actively working on it.
  • Resolved — the issue has been fixed. Kept in the list for history and reporting.
  • Issue — a stuck / parked state. Used when the team hasn't been able to resolve something in an acceptable timeframe and no clear solution exists. Flags the item for escalation or senior review — it's not just "open for longer", it's "we need a different approach".
The columns

One row per issue. Columns shown left-to-right:

Property (sortable)

The property the issue relates to. Click the column header to sort alphabetically A→Z or Z→A.

Issue

The short heading — e.g. "Water Leak", "Repair of elevator", "Parking Bay". Keep these concise; full detail belongs in Description and Comments.

Description

The longer explanation. Think of it as the "statement of the problem" when the issue was first raised — it doesn't update as the story evolves; that's what Comments are for.

Date Logged (sortable)

When the issue was first raised (dd/mm/yyyy). Click to sort oldest-first or newest-first.

Status (sortable)

Coloured badge (Issue / Unresolved / Resolved). Sort is urgency-ordered — Unresolved first, then Issue, then Resolved — so the most pressing items rise to the top.

Comments

A Comments button that opens the comment thread for this issue (see the Comments tab).

Delete (Superuser only)

A red bin icon. Only visible to Superusers. Opens a confirmation popup with full issue details before deleting.

Default sort: Property (A→Z), with Status as the tiebreaker (Unresolved first, Resolved next, Issue/stuck items last). Click any sortable header to change.
Four filters

Click the Issue Filters panel header to expand. All auto-submit on change.

Search

Full-text search across the Issue heading and Description fields. Type your query and either press Enter or click the teal search icon button.

Country

Cyprus, Greece or Spain — matches on the property's country.

Property

Narrow to a single property.

Status

Resolved, Unresolved or Issue. Default shows all.

Active tags & Clear All

Applied filters appear as removable tags below the dropdowns. Click × on any tag to drop that single filter. Clear All (top-right of the panel) resets everything.

Column sorting

Three columns are sortable: Property, Date Logged, Status. Click the header once for ascending, again for descending. Arrow icons show the current sort direction. Status sort is lifecycle-ordered (Unresolved → Resolved → Issue), not alphabetical — active work first, completed work next, stuck items last.

Common workflow: Set Status = Unresolved, then sort by Date Logged (oldest first). That's your "stale issues to chase" list — what should already have been resolved by now.
The Comments page

Clicking the Comments button on any row opens a dedicated page for that issue, showing:

  • The issue heading, description in brackets, date logged, property and status at the top
  • A text box to enter a new comment, a Save Comment button, and a Change Status dropdown (Resolved / Unresolved / Issue) to update status in the same step
  • A reverse-chronological thread of every comment, colour-coded by author type
Comment colour coding

Comments in the thread alternate colour based on who wrote them — a subtle background tint makes the back-and-forth easy to follow. Each comment is automatically prefixed with the date and the author's initials (e.g. (DM), (SS)) based on who's logged in — you never type these yourself. Just write the comment content; the system handles attribution.

Why it's a thread, not an "update" field

Every comment is preserved permanently. The issue description doesn't change; the thread grows. This gives you a full audit trail of what was tried, what happened, what was decided — invaluable when reviewing old issues or handing work to a new staff member.

Change Status + Comment in one go: when you mark an issue Resolved, always add a closing comment explaining what happened. Don't just flip the status silently — the audit trail suffers.
Adding a new issue

Click Add New (top-right) to open the Add Issue form. Five fields:

Property Name

Dropdown of all properties. Pick the one this issue relates to.

Date Logged (auto-filled)

Defaults to today's date. Read-only in most cases.

Issue Status (auto-filled)

New issues default to Unresolved. Can be changed later via the Comments page.

Issue Heading

Short, specific title — "Water Leak", "Fridge does not work", "Repair of elevator". This is what appears in every list and report.

Issue Description

A longer description — the full context at the time of logging. Think of it as "everything I know about this problem right now". Subsequent developments go in Comments.

Save commits the new issue; Back cancels without saving.

Deleting an issue (Superuser only)

Click the red bin icon in the Delete column. A confirmation popup opens showing:

  • Property, Status, Date Logged, Issue ID
  • Issue Heading and Description
  • A prominent warning that the action is permanent

Click Delete Permanently to confirm, or Cancel to back out.

Delete removes all comments too. The entire thread goes with the issue. Prefer leaving old Resolved issues in place — they're historically useful and don't clutter anything if you filter to Unresolved.
Three reports, each with its own purpose

Three teal buttons at the top-right open three different reports. Each first shows an options modal to narrow the output.

Comments Report

Shows every comment (not issue) posted in a chosen time window. Time period options:

  • Last 7 Days
  • Last 30 Days
  • Last 90 Days
  • All Comments

Output: one row per comment with Comment text, the parent issue link and description, Date, Property, Status, User (author initials) and a Delete bin. Author rows are colour-coded — Admin Comments and User Comments (legend at the top). Has a green Print Report button.

Resolved Issues Report

Shows every issue that was Resolved within a From / To date range you pick (defaults to the last 30 days).

Output: grouped by Property, with each resolved issue showing heading, description, and — uniquely to this report — a Resolution: N days metric showing how long the issue took to close. Below each issue, every comment in the thread is listed with date and author prefix.

Friday Status Report

The weekly update report, sent to stakeholders every Friday. Two flavours:

  • Detailed Report — every comment on every issue. Comprehensive but long.
  • Summarized Report — only the most recent N comments per issue (pick 1, 2, 3, 4, 5 or 10). Good for busy recipients who want the headline without the full history.

Output: grouped by Status (Resolved → Unresolved → Issue), then by Property (country, then name). Each issue shows heading, description, resolution days (if resolved), the selected comments, and a "View all comments" link when the thread was truncated. Resolved items are filtered to only those resolved within the last 7 days OR with a comment added in the last 7 days — this keeps the report focused on recent activity rather than cluttering it with every historical closure. Unresolved and Issue items are always shown regardless of age. Has a teal Submit FSR button in the header to commit the report.

Which report when? Comments Report = "what did we talk about recently". Resolved Issues Report = "what did we close in this period + how fast". Friday Status Report = the weekly snapshot you send to stakeholders.
Best Practices
  • Keep Issue Headings short and specific — "Water Leak" is better than "There's a problem with water". They appear in every report and list; scannability matters.
  • Put context in Description, updates in Comments — Description is the initial statement of the problem and shouldn't change. Comments are where the story evolves.
  • Always add a closing comment when marking Resolved — explain what fixed it. Six months from now someone will thank you.
  • Just write the comment — prefix is automatic — date and author initials like (DM), (SS) get inserted by the system. Focus on clarity of content, not formatting.
  • Sort by Status (urgency) + Date Logged (oldest) — Unresolved issues that have been open for weeks are the ones to chase first.
  • Use "Issue" status sparingly — it's for genuine escalations, not just items that have been open a while. Flipping something to "Issue" is a signal that the current approach isn't working and attention is needed. Most things that stay in Unresolved for a long time are simply slow, not stuck.
  • Use Search liberally — when a tenant mentions "the thing with the balcony", search "balcony" across all properties to find the right thread fast.
  • Comments Report weekly, Friday Status Report weekly — different audiences. Internal team wants the comments firehose; stakeholders want the Friday snapshot.
  • Summarized FSR with 2–3 comments is the sweet spot for most recipients — enough context to understand, not so much they won't read it.
  • Resolution days red in the Resolved Issues Report is a self-audit — anything over 30 days is worth asking "why did this take so long?". Feeds process improvement.
  • Don't delete Resolved issues — the history is valuable and doesn't clutter the default view (filter to Unresolved if you want the current worklist).
Delete is permanent and takes every comment with it. Reserve it for true mistakes (duplicate issue, wrong property, test data). Don't use it to "clean up" old stuff — that's what filters are for.
