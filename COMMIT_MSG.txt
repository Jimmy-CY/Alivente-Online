the field label is bold, seven days after the standard said so

base.html's standards block has stated the shape of a field since 9
September:

    label > strong        the field name, bold
    span.alv-req          the asterisk, if the field is required
    input.form-control    the control

and has said underneath it, in as many words, THE SWEEP HAS NOT HAPPENED.
This is that sweep: 191 labels on 29 pages, and no CSS at all.

IT WAS SETTLED AGAINST THE MAJORITY, WHICH IS WHY IT NEEDED A ROUND

The count on 9 Sep was 545 labels, 338 plain to 207 bold. The standard went
the other way anyway - because the model page and the two biggest Add
screens already agreed, and because a label is a LABEL, the same reason a
heading shouts. A standard settled against the majority is a standard that
does nothing until somebody sweeps, and for a week nobody did.

THE WEIGHT COMES FROM THE MARKUP, NOT FROM A RULE SOMEBODY HAS TO REMEMBER

    <label for="bill_name"><strong>Customer Name</strong>
                           <span class="alv-req">*</span></label>

exactly as customer_invoice_form.html - the model screen - already does it.
A strong element needs no stylesheet to be bold, so a new page gets it
right by copying the markup rather than by remembering a class.

WHAT COUNTS AS A FIELD LABEL - THE STANDARD'S DEFINITION, NOT A GUESS

A label that NAMES A CONTROL CARRYING form-control. That is section 3.6's
own wording and it excludes tab labels, checkbox and radio labels, and
labels that wrap their own input. The first draft of this swept help_page's
TABS, because a radio button happened to follow one of them - a tab is not
a field and it should not have looked like one to the tool.

SIX LABELS ARE NAMED AND LEFT ALONE, NOT COUNTED AND FORGOTTEN

The patcher rewrites one shape: an optional icon, the field name, an
optional required marker. Anything else is printed with its page and its
text and skipped, because guessing where the strong goes is how a sweep
breaks a page it was meant to tidy.

  three on generate_lease_agreement, reading
      <span id="tenant-name-label">Individual Name:</span>
  which has an id because JavaScript rewrites the text at runtime;

  one more there, and one on property_assets, carrying a hint -
  (auto-calculated), (up to 5 - JPG/PNG, 5MB each) - that is not part of
  the field's name;

  and one on projects_delete, which is not a field name at all but a
  sentence of instruction with a red DELETE in the middle of it.

A PAGE WITH NOTHING TO REWRITE CAN STILL HAVE SOMETHING TO REPORT, and the
first draft dropped exactly that case: it returned early the moment a
page's edit list was empty, which silently swallowed projects_delete, whose
ONLY field label is one of the six. The suite found it, because the suite
counts plain labels in the corpus rather than trusting the patcher's list.
That is the whole reason the two are written separately.

SCOPE GUARD #29 - AND THIS ONE I TALKED MYSELF OUT OF

The suite's section 3 began as a check: "no page makes a label bold with
CSS instead". It reads well and it is not this round's claim.

Ask what the claim is ABOUT. This round says every field label is bold FROM
ITS MARKUP. A page that bolds labels in CSS and omits the strong element
already fails section 2, which asks the markup and does not care what any
stylesheet says. So the only thing section 3 could catch that section 2
cannot is a page doing BOTH - which is redundancy, not drift, on pages this
round never opened. Deleting those rules is a CSS consolidation, and a
round that changes two things cannot say which one did it.

It reports now: thirteen page-local rules and one font-weight-bold utility
class, each named with its page, counted in the summary so they are not
forgotten, and with no ceiling - a count cannot tell a page leaving that
set from a page joining it.

ITS FIRST PATTERN COULD NOT TELL A CLASS FROM AN ELEMENT. \blabel\b matches
after a hyphen, so .detail-label and .report-year-label were reported as
label rules and the section found 53 where there are 13. The control on
that section is now the pattern itself, asserted against both spellings -
the only part of section 3 that can fail, which is the honest shape for a
section whose body is a report.

SECTION 4 IS THE ONE THAT EARNS ITS KEEP

The bold comes from an element, so it depends on no stylesheet - unless a
stylesheet takes it away. One `strong { font-weight: normal }` in base, or
a Bootstrap reset, would un-bold every label in the system and leave the
markup looking perfectly correct. Nothing that reads the templates can see
that. So section 4 renders a real field against base's real CSS in Chromium
and reads the computed weight back: 700 on the strong, 400 on a control
that is plain, the required marker beside the name rather than inside it,
and its colour read back from base rather than trusted.

A SKIPPED CHECK IS COUNTED IN THE SUMMARY. Eleven suites on this gate print
a SKIP line when Playwright is absent and then report zero failed - which
is how a fresh clone goes green having proved a third less than it looks.

SABOTAGED FOUR WAYS BEFORE IT WAS BELIEVED

Unwrap one strong inside one label and section 2 names the page. Change
base's stated shape and section 1 fails. Add a strong reset to base and
section 4 reads 400. Move the asterisk inside the strong and section 4 says
so. My first attempt at the first of those unwrapped an EMPTY <strong></strong>
in a messages block and the suite passed - a sabotage that changes nothing
proves nothing, and I nearly filed it as a hole in the suite.

VERIFIED: every suite in the repo run before and after. 81 report
identically; the one that differs is this round's own, failing before and
passing after. The patcher is idempotent, refuses to write if any page
fails its per-file check - visible words unchanged, label count unchanged,
tag balance unchanged, strong delta equal to the edit count, and everything
outside the labels byte-identical - and writes nothing at all when anything
fails. The round was also applied on top of the heading round and both
suites stay green, and the gate wiring anchors on the END of the suite list
rather than on the name of a neighbour, because the last entry differs
between this sandbox and the development machine.

NOT PROVED HERE: that bold is the right choice. That was settled on 9 Sep
against a count that went the other way. This only holds the system to it.
Look at Tenants > Add and any Financials add screen beside the model page,
customer_invoice_form.
