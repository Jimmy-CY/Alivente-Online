Entry sections push 3: the modals, the Assets deferral, and four screens
that came out with a reason

The last third of the round. 7 screens, 14 titles, 4 fields moved - and four
screens taken OUT after reading their markup, each for a reason the plan did
not know.

TWO RULES THIS PUSH NEEDED, AND NEITHER IS A LIST

A MODAL BODY IS ALREADY A PANEL. Four of these screens put their form in a
.modal-body, which is a box with a border, a shadow and a header bar. A
.form-card inside one is a panel inside a panel. So inside a modal a section
is a TITLE and nothing is wrapped round it - and the suite asserts those
four gained no panel, because "did not add something" is exactly the kind of
claim that rots.

A SECTION TITLE THAT NEEDS A COMPANION IS AN .alv-card. base declares
.alv-card properly - the card, its head, its title, its aside, its body, its
lead variant and its own print rules - and seven pages wear it. It is the
system's card with a header bar, where .form-card is the entry panel with
the wash. TWO COMPONENTS, ON PURPOSE.

THE LIFTS ARE ANCHORED, NOT INDEXED

purchase_invoice is not a row block: it is a bare .form-group after the
Warranty row, wrapped in {% if asset.purchase_invoice %} with a link to the
existing file inside the conditional. So both moves cut the block and
re-insert it as a row of its own above a named section title, each anchor
asserted to appear exactly once - AND THE SUITE COUNTS THE DJANGO TAGS,
because a block can lose the {% if %} that wrapped it and nothing about a
field list would show that.

THE GATE CAUGHT SOMETHING THIS ROUND DID NOT BREAK AND DID EXPOSE

test_label_bold.py stopped the push on edit_asset's "Purchase
Invoice/Receipt" - a field label with no <strong> in it, against a standard
set on 9 Sep. IT WAS ALREADY LIKE THAT. It sat in a bare .form-group outside
any row, where that suite's scan did not reach it, and lifting it into the
Purchase section put it in scope.

So the fix is to meet the standard, not to add an exception to the suite. An
exception would record that the rule does not apply there, and it does.
property_assets' "Photos (up to 5 ...)" label is plain too and is NOT
touched: that one is already named in test_label_bold.py's own exception
list, so it is a decision somebody made, and undoing another round's
decision is not this round's business.

AND A REAL BUG IN THE TOOL, FOUND THE SAME WAY

Re-running the patcher lifted the block AGAIN. blocks_all() finds the inner
block, not the .form-row the first lift wrapped it in, so a second run
wrapped it in another row and left the first one empty - a nested row per
run. The guard is that everything between the end of the block and the title
is closing tags and whitespace, which is what "already placed" means.
Idempotence is a claim; it has to be run twice to be one.

PROJECTS IS HELD, AND NOT FOR A LAYOUT REASON

project_tasks_edit renders five controls twice: an auto-calculated read-only
version and an editable one. Those auto-calculated values are computed for
display and NEVER STORED - a parent task has all six get_calculated_*
methods and nothing that calls them, while a Project has
update_project_from_tasks() and a signal that fires it. THE ROLLUP EXISTS
ONE LEVEL UP AND WAS NEVER IMPLEMENTED ONE LEVEL DOWN.

Show-ProjectRollup.py ships with this push: read-only, it reports which
parent tasks are stale, what each would become, the deepest nesting present
and how many would raise if saved. On the local database: 4 of 4 parents
stale, every one with an empty start date, an empty expected completion and
a zero budgeted cost, and one reading Pending while its subtask was under
way. 0 would raise. See claude/projects_auto_calculated_rollup.md.
