Save above the fields, and one way out of a form

Every Add and Edit screen should offer the same two controls in the same
two places. Most already did. This round fixes the ones that did not, and
a whole class of screen I had never looked at.

A SCOPE BUG OF MINE, FOUND BY A SCREENSHOT

Three rounds decided what an Add or Edit screen is with

    (_add|_edit|_form)\.html$

which matches asset_edit.html and NOT edit_asset.html. So edit_asset was
invisible to the panel round, the action-bar round and both their suites -
and it is exactly the screen that turned out to have Save at the bottom
beside a redundant Cancel. You found it by opening the page.

The pattern is widened rather than the filename added. It is the fifth
time a rule of mine has been narrower than the thing it names, and the
suite has a control proving the new one matches both spellings.

CANCEL AND BACK ARE THE SAME ACTION - EXCEPT WHEN THEY ARE NOT

A text search says eight screens carry both. THAT COUNT CONFLATES TWO
DIFFERENT CONTROLS. On three of them Cancel is a button with
data-dismiss="modal", which closes a DIALOG; removing it would break the
modal. On two more the page is a delete confirmation, where Cancel is the
safety control and means something Back does not.

So a Cancel is treated as a duplicate only when it is a LINK whose href
matches the Back link's on the same page - provable from the markup rather
than inferred from the word. Five screens lose one. On customer_form,
which had a Cancel and no Back, the Cancel BECOMES the Back, so the pair
is the same everywhere rather than absent on one screen.

SAVE MOVES ON TWO SCREENS, AND THE FIRST ATTEMPT MOVED THE WRONG BUTTONS

Taking "the first submit below the first control" picked up STATUS actions
- Approve, Send, Delete - on customer_invoice_form and
physical_invoice_edit, and a button inside a modal on
generate_lease_agreement. Moving any of those to the top would be
nonsense. It is the primary Save now: the one carrying action-primary,
outside a dialog, on a page that has no primary above the fields already.

edit_asset also loses the row its Save sat in, and the <hr> that separated
the fields from it - a divider with nothing left to divide.

login, my_profile and notification_settings also keep Save below their
fields and the name pattern does not call them entry screens. They are
REPORTED rather than moved: widening the pattern again is a decision, and
leaving them unmentioned is the same silence that hid edit_asset.

A FOURTH BAR VARIANT - AND THIS ONE IS NOT INERT

.page-action-buttons-single sets justify-content: flex-end and was
declared, identically, on three pages. The variant retired yesterday had
the SAME declaration and did nothing. This one does: below 768px base
removes the auto margin from .action-back, so this class is the only thing
keeping a lone Back on the right. Measured at 400px it is the difference
between Back at 8px and Back at 346px.

What decides it is what else is in the bar. A primary button eats the free
space, leaving justify-content nothing to distribute; a bar holding only
Back has space to give. Same stylesheet, opposite verdict - which nothing
static can tell apart, so the suite renders both and measures both.

base declares it now, the three copies go, and where Save joins a bar the
class comes off it, because the bar is no longer a lone-Back bar.

SCOPE GUARDS #32 AND #33 - TWO SUITES THIS ROUND BREAKS

test_button_reach required edit_asset to carry an action-secondary, which
was its Cancel. The claim was never "this page has a Cancel"; it was SAVE
IS THE ONLY PRIMARY AND THE WAY OUT IS QUIET. It asks that now, and covers
whichever quiet control the page ends up with.

test_table_lease_agreement listed .page-action-buttons-single among the
rules that MUST NOT have been deleted - a safety net against a patcher
taking too much. base declares it now and the page's copy went with the
move, so the net failed for the reason the round succeeded. It asks the
stronger question: the page must still USE the class and base must still
DECLARE it. A patcher deleting too much fails that just as hard, and a
later round quietly dropping the component from base fails it too, which
the old spelling would have missed.

FOUR CHECKS OF MINE WERE THE WRONG SHAPE, AND ONE OF THEM COST FOUR PROBES

Requiring the visible text to be unchanged, in a round whose purpose is to
delete a button. Then stripping the first "Cancel" from the page's
concatenated text, which removes whichever comes first rather than the one
deleted. It measures the SIZE of the change now: exactly as many visible
characters as the elements this round touched, and no more.

Requiring whole-page tag balance, when user_add, user_edit and
user_permissions have crossed <form> and <div> tags and have had since
before any round in this sequence - the oldest backup on disk already
shows it. It is a DELTA now: this round may not make them worse.

AND `\b` IN A PLAIN PYTHON STRING IS A BACKSPACE. The guard this round
writes into test_table_lease_agreement contained a word boundary that
became character 0x08, so the regex searched for a backspace, never
matched, and the check failed while the identical expression typed by hand
passed. Four probes to see it, because every tool that printed the line
rendered the backspace as nothing at all. The patcher now refuses to write
any file containing a control character.

VERIFIED: 12 checks, sabotaged four ways - re-add a duplicate Cancel, put
Save back below the fields, restore the narrow pattern, re-add a page-local
copy of the bar rule. Every suite run before and after with full output
compared: seven differ and all seven pass, including the two repaired here.

NOT PROVED HERE: that Save belongs at the top or that Cancel should go.
Both were decided from the screens themselves.
