Administration and Personal, stage B: the module heading

Seven of these eleven screens headed themselves in four different ways.
They head themselves the house way now.

A FOUR-PAGE SAMPLE IS NOT A SURVEY, AND I NEARLY REPORTED THE OPPOSITE

Looking for the shape to copy, the first four list screens I opened -
Tenants, Properties, Suppliers, Expenses - all used a bare
<h2><center>NAME</center></h2> with no class. From that it looked as
though base's heading standard covered entry screens only, and that
putting Administration on it would make this module the odd one out in
the other direction.

Counted properly, across the 90 property-management templates:

    46   on base's standard, .page-title-h2
    17   an h2 with a <center> and no class
    15   an h2 in some other shape
     6   an h1
     3   an h2 with an icon
     3   no heading at all

The standard is the plurality; those four screens are in the 17. So this
round moves Administration onto the standard AND onto what most of the
system already does. The 44 stragglers are a later round.

THE MODULE NAME IS DERIVED WHERE THERE IS ONE TO DERIVE

Same rule as the entry screens: follow the Back link and read the heading
of the screen it returns to. user_permissions returns to
user_administration, so it becomes USER ADMINISTRATION over PERMISSIONS —
{{ target_user.username }}.

A LANDING SCREEN IS ITS OWN MODULE. user_administration, workspace
management, help and my_profile have no Back at all; they ARE the top of
their module, so their own heading becomes the module line and there is no
mode line to invent.

admin_apms has a Back and it goes to `home`. THAT IS NOT A MODULE - it is
the system root, and deriving from it would head the Administration
dashboard with whatever the home page calls itself. Named, with the
reason, and treated as a landing screen.

AND A MODE LABEL DOES NOT REPEAT ITS MODULE. notification_settings calls
itself "Administration Notification Settings" and returns to
ADMINISTRATION, which would have given ADMINISTRATION over ADMINISTRATION
NOTIFICATION SETTINGS. Where the mode begins with the module name, the
prefix is dropped.

A SIXTH NAME FOR ONE HEADING

admin_apms headed itself with .admin-page-title, declared on that page and
nowhere else. Sixth name this system has had for one heading, after
page-title-h2, page-title-center, the bare centred h2, the h1 and the
icon'd h2. It goes with this round, and the suite requires all of the
retired ones to be absent from these modules.

THE ICONS GO. base's standards block says a heading carries no icon; six
of these seven started with one.

`&amp;` UPPER-CASED IS `&AMP;`, WHICH RENDERS

help_page's heading is "Help & User Manual". Upper-casing the literal text
turned its entity into &AMP; - which browsers mostly forgive, the standard
does not, and which would have survived for years precisely because it
LOOKS right on screen. The previous round protected Django tags from
upper-casing and not entities; this one protects both, and the suite
sabotages it.

VERIFIED: 11 checks, sabotaged four ways - drop the class, put an icon
back in a heading, rename a module on its own screen, upper-case the
entity. Every suite in the repo run before and after with full output
compared: five differ, four hold their verdicts exactly and the fifth is
this round's own.

STILL TO COME IN THESE MODULES: the panel on 5 screens, the panel title on
all 11, and the two tables.
