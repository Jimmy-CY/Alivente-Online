one action bar, and the variant that never did anything is retired

.page-action-buttons-form declared justify-content: flex-end. base also
declares .page-action-buttons .action-back with margin-left: auto. Same
specificity - and in a flex row an auto margin wins, because it consumes
the free space that justify-content would otherwise have to distribute.

So on every screen that has a Back button, which is all 49 entry screens,
the variant was inert. Rendered in Chromium at 1040px, 768px and 400px
with one, two and five buttons: a bar carrying the class and a bar without
it are identical in every button's position and size. It bites only on a
bar with NO Back button, which no entry screen is.

I SHIPPED HALF OF THAT RULE MYSELF, EIGHT DAYS AGO

The heading round put the desktop half in base and its commit message said
the variant "differed only in where it pushes its buttons". It does not
push them anywhere. I had read the stylesheet and not rendered it, which
is exactly the failure that round's own suite was built to catch for
:has() - and I did not apply the same suspicion to the rule beside it.

Before this, I told you 45 of 49 screens were "missing the right-aligned
form variant". They were not missing anything visible. That number was
wrong and the round it implied would have changed nothing on 45 pages.

IT WAS WORTH EXACTLY ONE PIXEL, AND THE SUITE SAYS SO

Below 768px the variant set align-items: stretch where the plain bar
centres. The Back button is 40px tall and the others 38px, so the plain bar
sits them 1px lower. That is the whole behavioural difference removed here,
on the four screens that carried the class. The first version of the suite
claimed the rules changed nothing at all; the browser contradicted it at
two of the three widths within a minute. The check now asserts what is
true: no horizontal change anywhere, and a vertical difference of at most
one pixel.

FIVE SCREENS MOVE SAVE TO THE TOP

customer_form, user_add, user_edit, workspace_add and workspace_edit put
their action bar at the BOTTOM of the form. Everywhere else it comes before
the first field. Save now lives in one place in this system.

Each bar is moved only if it is a self-contained div whose HTML tags and
Django block tags both balance inside it, and only into a form that opens
with a csrf token, so there is an unambiguous place to put it. A move is
checked as a PERMUTATION: the page's non-whitespace characters, its tag
list and its div and form balances must all be unchanged.

SCOPE GUARD #30 - A SUITE THAT REQUIRED THE RETIRED CLASS

test_heading_components asserted base defines three classes. Its claim was
that BASE OWNS THE CLASSES THE STANDARD IS WRITTEN IN, not that there are
three of them, so holding base to a class nobody should use would be
holding the system to a mistake. It asserts two now, plus that the third is
gone from base AND from every template - a stronger claim than the one it
replaces.

SCOPE GUARD #31 - AND A FLOOR CALIBRATED TO THREE CLASSES

The same suite required at least four guarded phone rules. Retiring one
class takes it to two, so the floor failed for the reason the round
succeeded. It is two now; the floor exists only so the check above it
cannot pass on an empty list, and the meaning lives in that line.

FOUR BUGS, AND THREE OF THEM ARE THE SAME BUG

A CHECK POINTED AT A SUBSTRING INSTEAD OF AT THE THING IT NAMES, three
times in one round. base's own note NAMES the class it retired - that is
what the note is for - so "is the string still there" found the
explanation and called it a survival. Twice in the patcher, once in the new
suite. All three ask for a class TOKEN or a RULE now, and the suite has a
control proving the pattern can tell `page-action-buttons-form` from
`page-action-buttons-form-x`.

One of those had a second edge: the rule pattern used [^{}]* to reach the
opening brace, which runs forward to the NEXT BRACE ANYWHERE - so with
prose in between it matched an unrelated rule further down the file. That
is the standards block's own documented lesson, prose shaped like code,
arriving inside the check written to enforce it.

AND THE MOVE WAS NOT IDEMPOTENT. Cutting the bar's lines and re-inserting
it is a no-op only if the tool RECOGNISES that the bar is already where it
is going; without that it re-inserted a newline and the indentation on
every run, so the file drifted a little each time. An idempotent tool has
to recognise the state it is trying to reach, not merely be able to reach
it.

TWO CLAIMS IN THE SUITE WERE TOO STRONG AND THE BROWSER SAID SO

Section 2 first required the bar to sit INSIDE the form element and be the
first thing in it. Eight screens put their bar above the form and two put a
heading inside the form above it - both ordinary arrangements that put Save
exactly where the decision says. The decision was about what the reader
sees first, so the check measures that: the bar comes before the first
control. That is one claim instead of two, and it is the one that was
actually agreed.

all five pass. test_entry_panel now reports 23 screens with the bar above
the panel instead of 19; test_filter_toggle counts base's braces at 347
rather than 351; test_standards_block counts one fewer component; and
