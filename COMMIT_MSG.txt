Seventeen of the twenty-seven entry screens already head themselves the

THE MODULE NAME WAS ALREADY WRITTEN DOWN

Not by me - on the screen each entry screen's Back button returns to.
customer_form's Back goes to customer_list, whose heading is INVOICE
CUSTOMERS. finance_expense_add's goes to finance_expense: EXPENSES.

So it is DERIVED: follow the Back link's {% url %}, find that template,
read its heading. A table of ten headings typed by me would have been a
list of filenames again, which is the thing that has been wrong five times
in this work. The suite re-derives all of it, so renaming a module on its
list screen reports its Add and Edit screens the same day.

THE MODE LABEL IS THE PAGE'S OWN WORDS, upper-cased - and only the LITERAL
text, never the inside of a Django tag. Upper-casing {{ workspace.name }}
gives a variable that does not exist and the heading renders EMPTY, which
looks like a blank line rather than an error. The suite sabotages exactly
that.

A FIFTH CLASS PAIR, IN ONE MODULE

The Issues screens headed themselves with .page-title-center and
.page-subtitle-center - text-align: center and nothing else, a strict
subset of what base's .page-title-h2 already does. All three Issues pages
are renamed, not only the entry screen, because fixing one would leave
that module internally inconsistent to fix a system-wide problem.

AND SINGULAR IS NOT DRIFT. Comparing headings as strings called three good
headings wrong - an entry screen naming the singular thing it edits beside

Four Issues phone rules that survived the rename and then styled classes

than dropped quietly.

pair, so it died part-way through instead of failing. A crash blocks a
push exactly as hard as a failure and says far less about why - the fourth
time that lesson has been earned in this project.
