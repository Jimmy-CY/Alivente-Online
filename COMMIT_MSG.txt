Gate round two: thirteen more suites, wired by a patcher that ran them first

THE GATE NOW RUNS 74 SUITES, up from 61. Every suite in the repo is now
either on it, repaired and waiting, or named as not belonging on it.

A SUITE THAT CANNOT PASS TODAY CANNOT HONESTLY BE WIRED ON TODAY. The 9 Sep
round wired thirteen suites on and discovered two had been failing for a day
and a half with nothing saying so; the lesson recorded then was that a suite
off the gate enforces nothing. This is the other half of it. Listing a red
suite does not enforce a standard - it stops every push until somebody
deletes the line, which is how a gate earns a reputation and then gets
bypassed with -Force.

So apply_gate_wire_two.py RUNS each candidate before listing it, wires the
ones that exit clean, and names the ones that do not without touching the
list for them. There is no separate survey step: a loop that reports,
followed by a patcher that acts on what the loop said, is two chances for
the two to disagree, and this project has already shipped a round where the
survey and the tree disagreed because the survey ran somewhere else.

TWO REPAIRS CAME OUT OF BUILDING THE PATCHER, both found before they could
block anything.

SCOPE GUARD #24 - test_print_media.py pinned "five phone blocks are
screen-only" and base now has six. The sixth is correct work: a later round
added a phone block and wrote the screen keyword, which is the standard
doing its job. A pinned count calls that a failure.

The claim is not "there are five of them". The round removed the ABSENCE of
the screen keyword from base's 768px blocks, because a bare max-width query
fires on PAPER - A4 portrait is about 718 CSS px - and shrinks the heading
of every printed report. So the claim is that EVERY 768px BLOCK IN BASE
CARRIES THE SCREEN KEYWORD, which is true of a sixth and of a seventh and
needs no number, with a floor as its control so it cannot pass on a base
with no phone blocks at all.

It deliberately does NOT widen to "base has no bare max-width query". Base
has one, at 991px, and twenty-seven PAGES carry the same fault. That is a
known outstanding item with its own round, and widening the check would
fail today for work this round never claimed to do.

test_comments_report.py CRASHED RATHER THAN FAILED. It read the index of an
@media print block the page no longer has - the print-leak round took it out
and handed the lot to base - so it died with ValueError instead of saying
so. Same printer fault that cost a push this morning, found this time by the
patcher that was about to put the suite on the gate.

It reads a find now, and handles both ends: a page with NO print block is
not a failure, it is the end state the print standard is driving at, and
which of the two it is gets said out loud.

SCOPE GUARD #25 - underneath that crash, in a section headed "the banner
belongs to its own round", a check asserting .stat-box still exists. That
round came and took it, and the page's own comment says why: a white
20%-alpha tile only reads on a dark ground, and base already owns the
component for a headline figure. The guard failed doing exactly what it was
built to do.

The answer is not to re-point it at whatever is there now. It is to assert
the END of the story instead of the middle: .stat-box has gone to base. Read
from the comment-stripped file, because the page still EXPLAINS the removal
in prose and reading the raw file finds the explanation and calls the
removal a failure - the same trap as the note twenty lines above it.

THE REPAIR DID NOT FINISH THE JOB, AND THAT IS WHY IT IS NOT WIRED. Both
faults above are fixed and the suite went from crashing to 48 passed 0
failed in the sandbox - but on the development machine, which has the data
the sandbox does not, it reports 73 passed and 1 failed. Something real
remains, visible only where the whole system is. It stays off the gate until
that is understood, and it is not going to be understood by guessing.

TWO FILES ARE NOT CANDIDATES AT ALL.

test_parser.py is renamed to probe_crs_parser.py. It is a smoke-test for a
CRS Excel parser with a hardcoded path into a Downloads folder, and it
asserts nothing - it prints what it found and exits 0 whatever that was. On
the gate it would be a check that cannot fail, and this project has now
shipped five of those. Out of the test_ namespace is where it belongs.

test_map_tiles.py is superseded by this morning's map-provider round. It
asserts the OpenStreetMap tile URL is a literal in map_view, that the tile
layer's only options are attribution and maxZoom, and that the attribution
credits OpenStreetMap - all true of the page that round replaced. Its
map_view regression half is still worth having, so this round neither wires
it nor deletes it. The patcher names it on every run so it cannot be quietly
forgotten. Rewriting it down to the claims that survive is a decision, and
decisions do not belong inside a sweep.

VERIFIED: the patcher is idempotent - a second run wires nothing and reports
the five it already did. Its wiring self-check refuses to write unless every
new entry lands exactly once and the last one closes the array. The renamed
file keeps the console-encoding preamble, and test_console_encoding still
reports 25 passed 0 failed with one fewer file in its corpus.

STILL OPEN, and worth saying plainly because it is the same disease as the
one this round is about: eleven of the suites now on the gate skip their
rendered sections when Playwright is absent, print a SKIP line, and then
report "0 failed" and exit 0. On the development machine Playwright is
installed and they run. On a fresh clone the gate would go green having
proved considerably less. test_notify_btns does the same with a missing
snapshot - 32 checks becoming 29 with nothing saying so. A summary line that
says "0 failed" after skipping a third of its checks is lying by omission,
and the fix is uniform: report skipped alongside passed and failed, and let
the gate surface it.
