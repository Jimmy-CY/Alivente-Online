The map leaves OpenStreetMap's volunteer tile servers, and two scope
guards stop holding snapshots they cannot keep

PROPERTIES > ADD STOPPED DRAWING. The map came up with a yellow-and-black
square over Cyprus:

    403  Access blocked
    App is not following the tile usage policy of OpenStreetMap's
    volunteer-run servers

Nothing in the app had changed. tile.openstreetmap.org is a volunteer service
under a usage policy written for OSM's own site and small, casual use, and
blocks are applied by referring domain - which is why every page went at once
rather than one of them. The OSM wiki lists the triggers and two of them fit
this code exactly.

FIRST, ATTRIBUTION WITHOUT A LINK. properties_add and properties_edit both
credited OpenStreetMap as plain text. map_view was the only one of the four
map pages that linked to the copyright page. An unlinked credit is on the
wiki's list of reasons an application gets blocked by hand.

SECOND, THE GEOCODER. "Find Address on Map" called OpenStreetMap's Nominatim
service straight from the browser. That service asks for an identifying
User-Agent, which a browser will not let a page set - so the call could not
comply however politely it was made. Separate service, same foundation, and
blocks travel together.

There is a third reason, quieter and more decisive: a property-management
system is a for-profit product, and the tile policy is not written for one.

MOVED TO GEOAPIFY. Free plan, 3,000 credits a day, a tile costs a quarter of
a credit, and the terms permit commercial use provided the attribution names
them. Their osm-carto style is the classic OpenStreetMap rendering, so the
map looks the way it looked before it stopped drawing. The same key serves
the address lookup, so the geocoder moves in the same change rather than
waiting to be noticed separately on some later afternoon.

Stadia Maps and MapTiler were both read and both rejected: their free tiers
exclude commercial use in as many words.

ONE DEFINITION, FOUR CONSUMERS. The URL, the attribution and the zoom ceiling
now live in mysite/context_processors.py and reach the templates through the
context. They used to be spelled out four times, and map_view's own comment
records what that cost: it had drifted to CARTO, CARTO began gating those
tiles behind a key, and CARTO does not fail without one - it returns tiles
with API KEY REQUIRED printed INTO the image. The map drew. The pins landed.
The console stayed clean. Every tile carried a watermark and nobody looked.

That is also why the keyless stopgap was refused when this round was agreed:
the last keyless provider is exactly how this got here.

THE KEY IS NOT A SECRET AND IS NOT IN THE REPO. A browser map key travels to
the browser; there is no arrangement in which it does not. It is protected by
being restricted to one origin in the provider's dashboard, not by being
hidden. So it comes from the environment - GEOAPIFY_KEY, set in Railway - and
git never holds it. A check in the suite fails if a key-shaped literal ever
appears in a template or in settings.

AND WITH NO KEY THE PAGE SAYS SO. The tile layer is not added at all, and
base's new .alv-map-nokey covers the map box with a sentence naming the
variable somebody has to set. A map with no basemap is an empty grey square,
and an empty grey square reads as a fault in the page rather than as a
setting nobody has filled in. That distinction is not theoretical - it is the
whole reason the CARTO drift survived for months.

WHAT THE SUITE DOES. test_map_provider.py is on the gate, taking it to 61.
Its section 2 RENDERS each page's map block through Django in BOTH key
states and reads the JavaScript that comes out. That is not decoration:
escapejs rewrites every one of the characters for less-than, greater-than,
ampersand, equals, minus and semicolon into a unicode escape, and the tile
URL contains four of them, so a check that read the template source would
never see whether what reached the browser was still a URL. It then decodes
those escapes the way a JavaScript engine would and compares the result to
the URL the context processor built.

Section 4 sweeps every template in every directory - not just the top level,
which is the shape of mistake that had me report the gate complete while the
development machine said nineteen suites were missing.

MAXZOOM STAYS AT 18, though Geoapify serves 20 and 20 would be better for
dropping a pin on one building. A round that changes two things cannot say
which one fixed it, and map_view's own comment already says that about this
same number.

map_test.html is a debug page and was migrated rather than deleted, so that
"all four pages configure the map identically" stays a checkable claim.
Deleting it is its own decision.

SCOPE GUARD #22 - test_standards_block.py, and the last snapshot in it.

This round added one component to base.html and touched nothing else, and the
gate stopped: "everything outside the block is byte-identical to the state
before the last run". Correct work, failed check, twenty-second time.

Guard #19 had already moved that comparison once - from the first-ever
snapshot to one refreshed on every run of apply_standards_block.py - and its
own comment explained why the first had failed: another agreed round edited
base. The second snapshot bought exactly one more round.

ASK WHAT THE CLAIM IS ABOUT. "This application of the patcher changed only
the block" is a fact about ONE RUN OF A DIFFERENT PROGRAM. A suite that runs
on every push cannot verify it: arbitrary time and arbitrary other rounds
pass in between, so any snapshot it holds has an expiry date - and a check
with an expiry date is a scope guard waiting to happen. The problem was never
which snapshot. It was that the claim did not belong in the suite.

So it moved into apply_standards_block.py, where both sides are in hand - the
bytes as found and the bytes about to be written - and where a failure means
the script has a bug and nothing should be written. Verified with a control:
a stray edit to base's title tag inserted into the patcher is refused.

WHAT STAYS IN THE SUITE is what that claim was protecting, in the present
tense. The fault being guarded is the comment block SWALLOWING one of base's
own tags, and that has two fingerprints needing no snapshot at all: a
swallowed tag is IN the body, and the body is already asserted to contain
nothing shaped like a tag; and a swallowed opening tag leaves its closer
stranded outside. The style and script tags outside the block must now simply
balance. Both claims are permanent, both work on a fresh clone, and base may
gain or lose a stylesheet without either of them caring.

The suite reports 60 passed, 0 failed, and reads no snapshot at all.

SCOPE GUARD #23 - test_required_sweep.py, and the sixth whole-file diff.

The gate stopped again, two files along: "and nothing else changed", for
properties_add and properties_edit. The required-marker sweep had asserted,
per page, that stripping the markers from the current file left it
byte-identical to its backup. This round edited the tile block in both,
two hundred lines from any label. Correct work, failed check.

AND IT WAS A DUPLICATE. apply_required_sweep.py already makes exactly that
comparison inside its own self-check, against the bytes it is about to
write, where both sides are in hand and the claim is true by construction.
The copy in the suite could only ever decay - the same diagnosis as #22, and
this time the claim was already sitting in the right place.

WHAT COVERS WHAT IS NOW WRITTEN DOWN IN THE SUITE, so the next person does
not have to work it out from three sabotage runs:

  - that the round changed nothing but markers: the patcher's self-check, at
    the moment it wrote the bytes;
  - that a marker was later REMOVED: section 3, which names any required
    field left unmarked and needs no backup at all;
  - that a marker sits where it belongs: a new per-page check in the present
    tense - every marker on the page is inside a label - immune to edits
    elsewhere in the file.

THREE CONTROLS were run against the replacement, and the first draft failed
two of them. Removing a marker and repointing a label both PASSED a check
that claimed to catch them, because the set it compared was the set marked
BEFORE the round, which is empty for a page that had none - a check that
could not fail, for the fourth time in this project.

Rewritten: removing a marker now fails section 3, and lifting one out of its
label fails the new check. Repointing a label's for-attribute at another
field fails NEITHER, and should not - section 3's rule accepts the nearest
preceding label, so that is a label-association fault and a different
standard. The
suite says so rather than implying a coverage it does not have.

ALSO NOTED, NOT FIXED HERE: test_map_tiles.py is superseded by this round.
It asserts the OSM tile URL is a literal in map_view, that the only options
are attribution and maxZoom, and that the attribution credits OSM - all
true of the page this round replaced. It is not on the gate, so it blocks
nothing, but it now describes a state that does not exist. Retiring it is
its own decision.

VERIFIED: 74 checks pass in the map suite, 60 in the standards suite, 41
in the required-marker suite in the sandbox. Four
sabotage controls were run against the map suite and each failed it for the
right reason - the attribution stripped of its link, a
key-shaped literal written into a template, the tile layer moved outside the
no-key branch, and one page pointed back at the volunteer servers. All 89
tools were run before and after this round: 83 are byte-identical and the six
that differ report counts that moved by exactly the size of the change - one
component, one brace pair, twenty-five lines of base, and two new files.

One of those controls CRASHED the suite rather than failing it, because the
check used an index lookup that raises when the substring is absent. It reads
a find now. A crash blocks a push exactly as hard as a failure and says far
less about why - that lesson cost a push this morning and was not allowed to
cost a second one from inside the suite written to record it.

NOT PROVED HERE: that tiles arrive. That needs a live request to a third
party, and a green answer would be a fact about one machine on one afternoon.
The previous map round said the same and was right to; what it could not say
was that the tiles had already stopped arriving, because nothing it could
check had changed. The remaining verification is a person loading Properties
and Add - and this time the page will say which of the two answers it is.
